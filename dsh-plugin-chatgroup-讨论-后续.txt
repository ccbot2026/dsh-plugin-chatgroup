## 1. 工作目录

原因：V1 实现里 AI 子 Agent 其实会继承**当前 dsh 会话**的 cwd，但群里没有把它存下来，界面和 prompt 也没显示，所以看起来像“没有工作目录”。

我刚补上：

- 建群时捕获当前会话的 `session.header.cwd`；
- 群快照里新增 `cwd` 字段；
- 群聊面板顶部显示：

```text
工作目录：/home/sll/projects/dsh-plugin-chatgroup
```

- 如果会话没有 cwd，显示“工作目录未设置”；
- AI 每次发言的 prompt 会明确写入：

```text
当前项目工作目录：/home/sll/projects/...
```

- 如果会话没有 cwd，AI 发言会直接标记为 `failed`，错误提示“当前 dsh 会话没有工作目录”，不会再去创建一个必失败的子 Agent。

一个当前架构限制需要你知道：**V1 不能给“群”单独设置与当前会话不同的 cwd**。`spawn` 子 Agent 的 cwd 来自父会话。所以要讨论哪个项目，就打开/创建哪个项目目录的 dsh 会话再开群。

如果“群内单独设置工作目录”是硬需求，我们下一版可以改成自己创建带 `meta.cwd` 的子 Agent，但 V1 先按继承会话目录实现。

## 2. 群聊面板和原聊天界面的关系

这是 V1 设计里刻意做的**两个独立空间**：

| | 主聊天界面 | 群聊抽屉 |
|---|---|---|
| 主体 | 当前 dsh 主 Agent | 1 个用户 + 最多 5 个 AI 群成员 |
| 消息去向 | 进入主 Agent 上下文 | 只存在群聊内存快照 |
| 谁发言 | 主 Agent | 调度器驱动的 AI 群成员 |
| 工具/文件 | 主 Agent 自己的权限 | AI 群成员只读工具白名单 |
| 持久化 | 正常 session 日志 | V1 内存态 |

**共同点**：两者属于同一个 dsh 会话，共享同一个 sessionId 和项目 cwd。

**没有共同点**：群聊消息不会进入主 Agent 上下文；主 Agent 不会自动看到或参与群聊；关掉群聊抽屉，主聊天完全不受影响。

我也把这句话加到了面板里：

> 群聊面板与主聊天独立：群聊消息不会进入主 Agent 的上下文。

这是 **deepseek-harness 自带的安全保护**，跟群聊插件无关。

## 原因

你尝试把沙箱模式：

```text
workspace-write  →  danger-full-access
```

dsh 检测到当前 dsh 会话里还有**打开的持久终端会话（persistent terminal sessions）**，所以拒绝提权。

设计逻辑是：

> 一个终端如果是在较低权限模式下创建的，之后把沙箱提升到 danger-full-access，那个终端就会在未重新约束的情况下变成高权限进程，存在逃逸风险。

所以 dsh 要求：**先关闭该会话下的所有持久终端，等正在创建的终端完成创建，再切换权限。**

## 解决方式

### 方式 A：让主 Agent 自己关闭终端

在**同一个 dsh 会话**的主聊天框里发送：

```text
请运行 terminal_list 查看当前所有持久终端会话，
然后用 terminal_close 把每一个都关闭。
关闭完成后确认没有任何终端会话。
```

等它回复“已全部关闭”后，再去切换权限。

### 方式 B：直接重启 dsh（最简单）

持久终端是**进程内状态**，重启 dsh 后会自动全部关闭：

```sh
# Ctrl-C 停掉 3081
dsh --profile dsh-chatgroup --port 3081
```

然后：

1. 打开原来的 dsh 会话；
2. 先切换到 `danger-full-access`；
3. 再开始让 Agent 打开终端。

注意：重启后群聊会按 V1 设计清空，需要重新建群。

## 3. 权限与安全边界

`toolFilter` 只是**工具可见性**，真正的写文件由 dsh sandbox 决定。

子 Agent 继承父会话沙箱策略，并且审批策略固定为 `never`。

因此：

| 会话沙箱模式 | 临时写权限结果 |
|---|---|
| `workspace-write` | 可写当前项目目录，推荐场景 |
| `danger-full-access` | 可写任意位置，风险高 |
| `read-only` | `write/edit` 可见但会被 sandbox 拒绝 |

建议：

- 勾选“允许写入”时，如果会话是 `read-only`，直接阻止并提示用户先切换权限模式；
- 或允许尝试，但把 sandbox 拒绝原因显示在群消息里。

我倾向**直接阻止**，避免 AI 执行到一半才失败。

---

## 4. 必须告诉你的限制

**V1 无法把写权限限制到“只允许写指定文件”。**

`toolFilter` 只能控制工具名，不能控制工具参数路径。

也就是说：

```text
@dsp --write 写入 docs/plan.md
```

执行期间 dsp 理论上可以调用 `write/edit` 写当前沙箱允许范围内的其他文件。

V1 只能：

- prompt 里明确指定目标文件；
- 依靠模型遵循；
- UI 明确提示风险。

如果必须做到**路径级硬限制**，需要下一版实现一个专用工具，例如：

```text
chatgroup_write_file
```

该工具由我们插件注册，只接受指定的一个路径，且只在临时写权限的 solo 发言中通过 `toolFilter.allow` 放行。这个方案更安全，但工作量明显更大。
