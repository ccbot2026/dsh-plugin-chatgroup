## 一、核心概念建议

| 概念 | 建议定义 |
|---|---|
| 群 | 一个逻辑聊天室，成员 = 人类用户 + 最多 5 个 AI |
| 成员 | `id / 类型(human|ai) / 角色(admin|member) / 名称 / AI配置(model、systemPrompt、temperature 等) / 发言顺序` |
| 发言轮 | 用户发起后，AI 按管理员设定顺序依次各发言一次，轮次结束 |
| 总记录 | 群内所有消息的完整记录，持久化保存 |
| 可见视图 | 发给某个 AI 时，根据可见性设置从总记录计算出的消息集合 |

## 二、需要先拍板的 8 个问题

### 1. 群里有几个人类？
现在的痛点描述像“**我 + 多个 AI**”。如果是这样，V1 建议：

> 1 个人类 = 初始管理员；AI 不设管理员角色，管理员只能是人类。

“管理员/普通用户”这套角色先保留在数据模型里，为将来多人做铺垫。**问题：V1 是否明确只支持 1 个人类用户？AI 可以成为管理员吗？**

我的建议：V1 只支持 1 个人类，AI 不能当管理员，权限逻辑最简单。

### 2. AI 成员是“聊天成员”还是“完整 Agent”？
- **聊天成员**：每轮一次 LLM 调用，生成一条回复，不能调工具、读写文件。成本可控、行为可预测，适合 V1。
- **完整 Agent**：每个 AI 是独立 Agent，有工具、能跑代码，可能产生多步任务、审批、并发问题，复杂度高很多。

**问题：AI 成员第一版要不要能调工具？** 我建议 V1 做“纯聊天成员”，但配置项保留 systemPrompt/model，方便以后升级。

### 3. 群的生命周期和存储范围
- 群是**属于当前 dsh 会话**，还是**应用级/跨会话存在**？
- 支持同时多个群，还是同时只跑一个活跃群？

这影响持久化方案：会话内可以用 append-only 的 `session events` 重放；跨会话就要上 `ctx.storage` 之类的独立存储。我建议 V1：**一个会话内可有多个群，但同一时间只允许一个群处于“发言中”**。

### 4. “一轮”的触发和结束语义
- 用户发一条消息，是否自动开始一轮（AI 依次各说一次）？
- 轮次结束后，谁可以发起下一轮？用户再发消息就开新轮？
- 用户是否参与固定顺序，还是用户永远可以随时插话？

我的建议：

> 用户随时可以发言；用户发言结束即开启/延续一轮 AI 发言；AI 按顺序各说一次后轮次结束；AI 不会主动发言。用户可以用 `/group stop` 中断。

### 5. “消息可见”的精确语义
这句最需要细化。我理解你想要的是第一轮“盲发”：

- 第一轮时，每个 AI 只看到**用户最初的议题**，看不到其他 AI 的第一轮回复；
- 第一轮全部结束后，所有消息再公开；
- 第二轮开始，大家都能看到第一轮内容。

**问题确认：**
1. 不可见是指“其他 AI 的消息不可见”，用户始终能看到全部消息，对吗？
2. 是否只有第一轮盲发？还是管理员可以指定任意一轮盲发？
3. 盲发期间，消息是“完全不存在于该 AI 上下文”，还是“存在但标记隐藏、由调度器过滤”？（我建议调度器过滤，记录完整但注入时裁剪。）

### 6. @ 的精确语义
- @ 是**一次性插队**还是**改变固定顺序**？
- 是插到当前发言人之后，还是本轮流到谁就由 @ 决定？
- 可以一次 @ 多人吗？多人按什么顺序？
- AI 能否 @ 别人，还是只有用户可以 @？
- 关闭 @ 时，消息里的 @ 是忽略、报错，还是只作普通文本？

我的建议，语义简单且可预期：

> @ = 一次性插队。当前发言人结束后，先处理被 @ 的人，再回到固定顺序；@ 多人按消息中出现的先后 FIFO；AI 是否可 @ 由管理员单独开关；功能关闭时 @ 按普通文本处理。

### 7. 发言失败/超时/中断
AI 可能超时、限流、报错，也可能用户想中途改主意。建议：
- 单成员失败：重试 1 次，再失败则记录“发言失败”，跳到下一位，不阻塞整轮；
- `/group stop`：立即中止当前发言，本轮结束；
- `/group retry @B`：让某个失败成员重新发言；
- 轮次中修改成员/顺序：**下一轮生效**，不影响正在进行的轮次（最不容易出 bug）。

**问题：单个 AI 的单次回复要不要限制 maxTokens？是否给整轮设预算/超时？**

### 8. 交互形态
这是实现路径的分叉点：
- **A. 斜杠命令版（快）**：`/group create`、`/group start`、`/group say`、`/group members` 等，消息以会话事件/命令结果展示。
- **B. Web 聊天 UI 版（完整）**：独立群聊面板，像微信，支持 @ 选人、成员管理界面、消息气泡、流式输出。
- 理想最终形态是 B；第一版可以先做 A + 完整事件模型，后面 UI 只做渲染层。

**问题：第一版接受“命令驱动、会话内展示”，还是直接要独立聊天 UI？**

## 二、先解释“一个会话内可有多个群”

意思是：**同一个 dsh 会话里，可以同时存在多个互相独立的群**，每个群有自己的成员、发言顺序和聊天记录；会话关闭/删除，这些群也随之消失。

例如你可以在当前项目会话里建：

- “需求讨论群”：AI-A、AI-B、AI-C
- “代码评审群”：AI-C、AI-D

**我的建议**：V1 先做 **1 个会话 = 1 个群**。数据模型里仍保留 `groupId`，调度器和 UI 按“多群可扩展”设计，但功能上先只允许一个，减少界面和状态复杂度。如果你确实想同时开两个群，我们也可以把“多群 + 群切换”放进 V1，但工作量会明显增加。

## 三、关于“AI 要只读探索项目文件”：不能直接走 `ctx.llm`，应走 `ctx.subagents`

你记得没错，deepseek-harness 可以接其他大模型，但这里**不要**从 `ctx.llm.stream` 入手。因为纯 LLM 调用只能生成文本，无法执行工具、读取文件。

源码里正好有更合适的机制：`ctx.subagents`。我的建议是：

> **每个 AI 的每一次发言 = 一个 one-shot 子 Agent**，使用 `spawn` provider。

```ts
ctx.subagents.start('spawn', {
  parent: currentAgent,
  prompt: buildVisiblePrompt(ai, group),
  agentOptions: { provider: 'deepseek', model: 'deepseek-chat' }, // 每个 AI 可不同
  toolFilter: {
    allow: ['read', 'read_image', 'glob', 'grep'],
  },
  signal,
})
```

这样：

- **模型可换**：`agentOptions.provider/model` 直接选择已注册的任意模型，比如 DeepSeek、其他 OpenAI 兼容模型；插件本身不用写任何模型适配器。
- **只读探索文件**：`toolFilter.allow` 只放行 `read`、`read_image`、`glob`、`grep`；`bash`、`edit`、`write`、`subagent` 等全部不可见、不可执行，天然满足 ReadOnly。
- **上下文干净**：`spawn` 的子 Agent 不继承主会话历史，调度器给什么它就只能看到什么。这对第一轮盲发非常关键。
- **结果可等待**：`SubagentRun.result` 在子 Agent 本次发言结束时 resolve，调度器可以严格串行安排下一位。
- **超时可控**：用 `AbortController` + 300s 默认超时，超时即取消并记录“发言超时”。

每个 AI 的成员配置保存在群里：`{ name, provider, model, systemPrompt, order, role }`；每次发言临时创建一个子 Agent，发言结束销毁。这样 V1 不用维护 5 个长期存活的子会话。

> 如果以后希望 AI 成员拥有“跨轮次的私有记忆”，可以平滑升级为 `ctx.subagents.startContinuable`，但 V1 不建议上。

```text
idle
  → 用户发言 → running(按顺序: AI1 → AI2 → ... → AI5)
  → 全部发完 → idle（本轮结束）

running 中用户插话：
  - 消息记入群记录
  - 不改变当前发言人和后续顺序
  - 当前 AI 看不到（请求已发出）
  - 还没发言的 AI 能看到
  - 已发言的 AI 下一轮才能看到
```

### 4.2 结束按钮

- Web UI 提供**结束按钮**，底层执行同一条 `/group stop` 命令；斜杠命令继续保留给键盘用户。
- 语义：立即取消当前 AI 发言、清空待处理的 @、本轮结束。
- 若第一轮被中途结束，已产生的 AI 发言仍然保留，并在下一轮开始后对所有人可见。

### 4.3 第一轮盲发

- “第一轮”我理解为**群创建后的第一个完整 AI 发言轮**，不是每个新话题的第一轮。
- 盲发期间，每个 AI 的 prompt = 成员身份说明 + 用户开场消息 + 该 AI 发言前的用户插话；**不含其他 AI 的第一轮回复**。
- 全部 AI 发完或本轮结束后，完整记录公开，第二轮起不再过滤。
- 用户界面始终显示所有消息。

### 4.4 @ 语义

- @ 是**一次性单成员回应**，不是修改固定顺序。
- 群里空闲时 @A：只调度 A 回应一次，其他 AI 不动。
- 轮次进行中 @A：当前发言人结束后插入 A 的回应，A 回应完继续原来的顺序。
- V1 只允许**一个 @ 目标**，只允许人类使用；AI 不能 @。
- @ 功能关闭时，消息里的 @ 按普通文本处理。

## 五、一个必须先拍板的技术风险：持久化

我查了 session 持久化机制，发现一个会直接影响方案的点：

> 外部插件的自定义 session 事件类型，当前 **重启加载时会被 deepseek-harness 拒绝**（除非事件带 `ignorable: true`，但 `Session.append` 还没有开放这个标记）。

而“群属于当前 dsh 会话”如果意味着**会话重开/进程重启后群还在**，有三个选择：

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 内存态 | 群只存在于进程运行期间，重启后消失 | 最快，适合先跑通；但可能不符合“属于会话”的预期 |
| B. 给 deepseek-harness 打一个小补丁 | 让 `Session.append` 支持给外部插件 log-only 事件标记 `ignorable: true`，群消息写进当前 session 日志，重启后由插件重放 | 最干净，改动很小；群事件不影响主 Agent 上下文 |
| C. 插件自带存储 | 群数据写到独立 JSON/SQLite，不碰 session 事件 | 不依赖核心改动，但要自己管生命周期、清理、跨重启恢复 |

我推荐 **B**。这也正好是 deepseek-harness 源码注释里明确预留、等待“第一个外部消费者”出现的场景，chat-group 很适合做这个消费者。

**问题：你希望群在 dsh 重启、会话重新打开后仍可恢复吗？**  
- 是 → 选 B，我会把最小核心补丁一并设计进来；
- 否 → 选 A，V1 会快不少。

## 六、Web UI 落点

我建议 V1 做**独立群聊面板/抽屉**，从会话头部按钮打开：

- 主聊天区继续留给 dsh 主 Agent，不劫持现有输入框；

## 1. “内存态 + 不动源码”的正确姿势

既然不能给自定义 session 事件打 `ignorable` 标记，方案明确为：

> **完全不写自定义 session 事件**，群状态只放进程内存。

这样重启后：

- 群聊干净消失；
- 会话日志没有被污染，原会话仍能正常加载。

Web UI 和 Host 之间改用自定义 RPC channel：

```text
Client: ctx.connection.rpc.call('/chatgroup', 'snapshot' | 'wait' | 'send' | ...)
Host:   ctx.connection.rpc.handle('/chatgroup', handler, { authority: 'trusted-host' })
```

不依赖 Typert Remote 代码生成，也不需要修改 `api-remotes`。实时性用 `wait` 长轮询 + `revision` 版本号实现。

## 2. AI 只读探索文件：one-shot 子 Agent

每个 AI 每次发言：

```ts
ctx.subagents.start('spawn', {
  parent: currentAgent,
  prompt: visibleTranscriptPrompt,
  agentOptions: { provider, model },      // 每 AI 可接不同模型
  toolFilter: { allow: ['read', 'read_image', 'glob', 'grep'] },
  maxDepth: 1,
  signal,
})
```

- `spawn` 保证子 Agent 看不到父会话历史，盲发裁剪才真正有效；
- 白名单天然实现 ReadOnly；
- `SubagentRun.result` 让调度器能严格串行推进；
- 超时由 `AbortController` 控制，默认 5 分钟。

## 3. Web UI 落点

- 入口：`conversation.session.header.actions` 加“群聊”按钮；
- 面板：注册到 `shell.overlay` 的独立抽屉，不替换主聊天区；
- 按钮操作走 RPC，不在主会话产生 command 卡片；
- `/group ...` 命令保留给键盘用户，与按钮共用同一个 `ChatGroupService`。
